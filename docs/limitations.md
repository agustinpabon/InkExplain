# Limits and known issues

What InkExplain does not do, and what is still unsettled. The README links here instead of listing it.

- InkExplain ships no image model. Image quality depends on the tool your agent uses, and real renders exist for all eight characters (one image each, on eight different ideas, from Codex Desktop), none scored with the review protocol. How a character holds up across a series was tried for Xiaohei only, in Codex, with a few series; see [the evaluation](evaluation.md#character-lock-and-repository-explanations-2026-10-18) for what held and what did not.
- Image models misspell labels, non-Latin scripts most of all. Keep labels short and review them.
- Stickman is `experimental`: its pack and reference sheet are complete, but no render has been reviewed, so each delivery says so. The gallery images in `examples/gallery/` are copies from the projects InkExplain builds on; none was generated for this project.
- Some agents send a generic image request ("create four illustrations") to an image skill of their own. Name InkExplain in the request, or start with `$inkexplain` in Codex, to be sure.
- Claude Code and Gemini CLI have no built-in image generator, and Cursor's and Google Antigravity's were not tested: see [image generation by host](usage.md#image-generation-by-host). This project has not run InkExplain in Antigravity itself. Four of one user's requests are analyzed in [the evaluation](evaluation.md#pictures-that-are-hard-to-read-2026-10-20): the packaged reference reached every image call, and each later request made new images in a fresh run folder. The second approved five images of which two had a white band across the black body and two had scribbles in it. The third and the fourth kept the character and made pictures that were wrong or hard to read (a level balance over unequal totals, three unrelated rules in one scene, a belt across the body), and the review accepted them. The rules changed after each of them, and the latest text has not been run in Antigravity. [The smoke test](evaluation.md#smoke-test-for-google-antigravity) is the request to try, and `scripts/audit-run.mjs` checks the result.
- Reference images: only Codex's image tool is known to take one, and a host that cannot take one runs on the written identity lock alone, which is weaker. Xiaohei, the Go Gopher, and Stickman bundle a reference; the other characters have none, so their series rest on the written lock. Whether a generator keeps a design across a series is its own property, and InkExplain can only supply the picture, check the results, and say what it saw.
- A run's record (`manifest.json`) is written by the agent. It makes a false claim checkable and does not make it impossible: the host's own log of the image calls is the authority, and some hosts keep none that the agent or the user can open. The counts in a report are only as good as that log.
- The series review is the agent's own, and the record says so (`reviewed_by`): it looks at each saved image next to the reference and writes what it sees and every flaw it finds. It is a stricter procedure than before, and it is still a model looking at pictures: a real run approved five images while two had a white band across the body, and a Codex run went the other way, rejecting every attempt on small matters of degree until the limit of six repairs left it with no approved picture. The rules now separate a defect (a rule broken) from a matter of degree, and that has been seen on a partial run only. The audit fails an approval with nothing on record behind it, a recorded defect that was approved anyway, and repairs past two for one image or six for the run. It cannot see the picture, so only another agent or a person catches what the first one missed. The same holds for the review of what a picture says (its numbers, the order of its stages, who may do what, its labels): it is written by the agent that drew the picture, the audit can say that it is on record and coherent but not that it is true, and a metaphor that reads wrongly can still pass an agent that does not read it literally: in the fourth run it recorded "accurate" for a picture of three unrelated rules. An agent that cannot view images reports "unable to verify". Read the images yourself before you publish a series.
- A repository explanation covers only the files the agent read, and lists them, so that the count can be checked against the list. It starts with what the project is and what a person can do with it, then the flows, the code's organization, and the principles. A large project gets an overview and a path for continuing, not a claim to have explained every file. Claims taken from documentation are labeled as documentation, `scripts/check-explanation.mjs` fails an explanation that calls something impenetrable or unbreakable, and the reading is only as good as the agent's.
- Third-party archetypes carry their owners' terms, and not every right is settled: [provenance.md](provenance.md) lists what is still open.
- The README translations were produced with AI assistance, have not been reviewed by professional translators, and follow an earlier layout of the English page, so they may lag behind it. Generated lists keep registry data in English.
- The offline gallery (`examples/gallery/index.html`) is one file you open from a checkout; it is not hosted.
